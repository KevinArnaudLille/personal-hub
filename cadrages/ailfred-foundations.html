CA1 · FONDATIONS

Ailfred, assistant personnel. cadrage-ailfred-foundations

Ailfred remplace à terme le seul Personal Hub : un espace personnel privé, extensible à des proches via des accès restreints, construit et opéré majoritairement par Hermes sous contrôle explicite de Kevin.

RECOMMANDATION RETENUE

Clever Cloud + ZITADEL, avec frontière Docker explicite

Choix confirmé : Clever Cloud pour les runtimes Docker et PostgreSQL managé ; ZITADEL pour l’identité OIDC/OAuth2 et le MFA. Le poste qui héberge Hermes exécute l’environnement local avec Docker Compose.

Docker Compose est le contrat de développement, non l’unité de déploiement : Clever Cloud ne prend pas en charge Compose. La production construit une image par application — initialement Java/Spring Boot contenant les artefacts Nuxt statiques ; le service IA Python est différé.

Le chiffrage de référence reste celui du cadrage Stack web européenne : environ 18,80 €/mois hors TVA, nom de domaine, stockage, trafic et consommation LLM. Les comptes Clever Cloud et ZITADEL ne sont pas encore créés.

PÉRIMÈTRE V1

Une landing page réellement protégée

  • Route de landing inaccessible sans session : Spring Security redirige vers ZITADEL ; le navigateur ne reçoit aucun secret OIDC.
  • Nuxt génère des fichiers statiques ; Spring Boot les sert et conserve la session OIDC côté serveur.
  • Une sonde technique publique est autorisée ; toutes les futures routes métier restent protégées par défaut.
  • Ni migration des données/fonctionnalités du Personal Hub, ni IA, ni invitation de proches, ni stockage métier ne font partie de cette initialisation.

DDD ET ARCHITECTURE HEXAGONALE

Le domaine avant les fonctionnalités

Ailfred suit strictement le Domain-Driven Design. Toute fonctionnalité commence par un cadrage de domaine : sous-domaine, bounded context, acteurs, invariants, commandes, événements et langage ubiquitaire. Ce langage est versionné et utilisé dans le code, les API, les tests et l’interface.

  • Contexte initial : identity-and-access, sous-domaine de soutien. Il authentifie via ZITADEL et porte les règles d’accès, sans mot de passe local.
  • Contextes différés : assistant personnel, connaissances personnelles, relations de confiance, orchestration IA et notifications. Chacun aura son propre cadrage avant toute implémentation.
  • Hexagonal : le domaine ne dépend ni de Spring, HTTP, SQL, Docker, ZITADEL ni d’un LLM. Les cas d’usage dépendent de ports ; les contrôleurs, OIDC, bases et providers sont des adaptateurs.
  • Règle de qualité : les invariants métier sont testés sans framework. Une modification de domaine met à jour le glossaire et les tests de contrat.

RÉPOSITORIE ET AUTONOMIE

Un compte GitHub dédié à créer, avec limites nettes

Le dépôt Ailfred sera détenu par un nouveau compte GitHub dédié à Hermes. Il sera relié à l’adresse Gmail professionnelle de Kevin via le filtre qu’il configurera. Ce compte ne remplace pas l’autorité de Kevin : il est une identité de livraison, pas un propriétaire autonome.

  • Hermes peut créer des branches, coder, exécuter les tests, préparer les PR et la documentation.
  • Kevin valide le compte et sa récupération, le dépôt, les protections de branche, les collaborateurs, les comptes Cloud/ZITADEL, secrets, utilisateurs de confiance, merge et déploiement de production.
  • Le dépôt interdit secrets, clés, états Terraform, dumps et données personnelles réelles. Les secrets runtime viennent du provider ; ceux de CI utilisent une durée de vie minimale, OIDC GitHub étant préféré si le provider le permet.
  • Les PR imposent formatage, tests, analyse statique, scans de secrets/dépendances/images, vérification Compose et une revue humaine renforcée pour identité, droits, session, redirection ou déploiement.

OBSERVABILITÉ

Provider d’abord, indexation seulement si nécessaire

Clever Cloud collecte les logs applicatifs via Vector et permet de consulter les logs et access logs dans la console, Clever Tools ou l’API. La rétention annoncée est de sept jours ; c’est suffisant pour la V1, le diagnostic et les alertes courtes, mais pas pour une recherche historique durable.

Les métriques CPU, RAM, disque et réseau sont fournies dans la console/Grafana ; des alertes Grafana sont configurables. Nous adoptons des logs JSON structurés vers stdout, sans tokens, secrets, sessions, corps de requête, claims OIDC ni données du Personal Hub.

Décision : pas de plateforme de logs additionnelle au départ. Si la conservation de sept jours devient insuffisante, un log drain Clever Cloud exportera vers un stockage de logs européen dédié, avec rétention, coût, accès et effacement explicitement définis. Le serveur Hermes ne devient pas un coffre de logs de production sans ingress sécurisé, sauvegardes chiffrées et responsabilité opérationnelle.

ANALYTICS FRONTEND

Umami auto-hébergé, isolé d’Ailfred

Solution retenue : Umami auto-hébergé, gratuit et doté de son interface d’analyse. Il utilise son propre PostgreSQL et une stack Docker Compose distincte ; la collecte est séparée des logs applicatifs et de la base Ailfred.

  • En local, l’interface Umami s’exécute sur le serveur Hermes uniquement en loopback pour Kevin, sur http://127.0.0.1:3001.
  • Pour mesurer les visiteurs d’Ailfred en production, son endpoint de collecte devra être accessible en HTTPS depuis les navigateurs — ou relayé par un proxy Ailfred. Un processus uniquement local à Hermes ne peut pas recevoir les événements des navigateurs publics.
  • Le tracker Nuxt ne sera ajouté qu’après création de l’URL HTTPS et de l’identifiant de site Umami. Aucune donnée d’analytics n’est encore envoyée.
  • Base Umami privée, secrets hors Git, télémétrie produit désactivée, mot de passe administrateur initial remplacé immédiatement. Replays de session et heatmaps exclus sans cadrage confidentialité/consentement distinct.

DÉCISIONS CONFIRMÉES

  • Nom du projet : Ailfred.
  • Option 1 de la stack européenne : Clever Cloud + ZITADEL.
  • Docker et Docker Compose sont obligatoires en local sur la machine Hermes.
  • V1 : landing page après authentification ; migration du Personal Hub dans un cadrage distinct.
  • DDD, langage ubiquitaire et architecture hexagonale sont obligatoires pour tous les composants.

PLAN D’EXÉCUTION — PRIORITÉ ABSOLUE

Prochaine étape : séquence, responsabilités et critères de sortie

Ce plan est l’ordre d’exécution d’Ailfred. Hermes exécute tout ce qui est techniquement automatisable ; Kevin ne réalise que les actions qui engagent une identité, un contrat, un paiement, une récupération de compte ou un droit d’accès humain. Aucun secret ne passe par Telegram, Git ou les logs.

0 · Poste Hermes — fondation d’autonomie

  • Hermes — à faire maintenant après ce cadrage : installer en espace utilisateur, sans sudo, les outils absents : Clever Tools, Terraform, Gitleaks, Trivy, Actionlint, Cosign et Syft ; vérifier leurs versions ; les documenter dans le dépôt et automatiser leurs contrôles dans CI. État constaté : Git, GitHub CLI et Docker sont présents ; ces outils spécialisés ne le sont pas ; sudo demande un mot de passe et n’est donc pas une dépendance.
  • Hermes : conserver le scaffold local, la skill Ailfred, les règles DDD/hexagonales, les tests, Compose et les contrôles de secrets. Créer ensuite les scripts reproductibles de vérification, pas des procédures manuelles fragiles.
  • Critère de sortie : une commande locale produit versions, tests, scan de secrets, scan d’image, validation Compose et rapport lisible ; aucune donnée réelle n’est requise.

1 · Identités fondatrices — intervention unique de Kevin

  • Kevin seul : créer le compte GitHub dédié Hermes avec l’adresse Gmail professionnelle, accepter les conditions, activer MFA, définir récupération et conserver les codes de secours. Configurer le filtre Gmail destiné à ce compte. Transmettre uniquement le nom d’utilisateur GitHub à Hermes, jamais un mot de passe ni un token par chat.
  • Kevin seul : créer les comptes Clever Cloud et ZITADEL, accepter contrats/DPA/facturation éventuelle, choisir la région européenne, activer MFA et récupération. Le propriétaire légal reste Kevin.
  • Hermes : ouvrir les flux de connexion CLI lorsque Kevin le demande ; Kevin valide dans son navigateur. Hermes ne lit ni ne stocke mots de passe, codes MFA ou tokens en clair.
  • Critère de sortie : GitHub, Clever Cloud et ZITADEL disposent chacun d’un propriétaire humain, MFA, récupération et région/conditions vérifiées.

2 · Dépôt et livraison continue — Hermes

  • Hermes : s’authentifier avec gh sous le nouveau compte après validation navigateur ; créer le dépôt privé Ailfred — choix recommandé pour un assistant personnel — puis y relier le scaffold local, réaliser le commit initial et pousser main.
  • Hermes : créer labels, modèles d’issues/PR, CODEOWNERS, Dependabot, CI de build/test/lint/secret-scan/image-scan/SBOM, artefacts Docker immuables et politique de branches courtes.
  • Hermes : appliquer la protection de main : pas de push direct, PR obligatoire, checks obligatoires, aucune force-push ; préparer les PR et corriger les échecs.
  • Kevin : approuve une seule fois les protections et reste approbateur/mergeur de main. Hermes ne fusionne pas ni ne déploie en production sans accord explicite.
  • Critère de sortie : une PR de test passe tous les checks, ne peut pas fusionner sans validation Kevin et chaque build est traçable à un commit.

3 · Identité, secrets et landing réellement connectée

  • Hermes : produire le bootstrap ZITADEL déclaratif (Terraform), qui crée organisation Ailfred, application OIDC Web, rôle user, callbacks exacts, utilisateur de test et configuration Spring. Tous les états Terraform, clés machine et secrets restent hors Git.
  • Kevin : valide dans ZITADEL les organisations, droits administrateur, DPA/région et toute création/modification de rôle, application, utilisateur ou politique. Il fournit l’accès par une connexion navigateur/secret manager, jamais en clair dans une conversation.
  • Hermes : injecter les secrets dans le mécanisme prévu par le provider, exécuter le test de connexion OIDC de bout en bout, puis vérifier qu’un utilisateur sans user ou avec un rôle d’un autre projet est refusé.
  • Critère de sortie : la landing production est inaccessible sans session, accessible avec le rôle Ailfred attendu, et les tests négatifs de droits passent.

4 · Hébergement Clever Cloud — préparation Hermes, validation Kevin

  • Hermes : préparer les Dockerfiles de production, migrations, health checks, logs JSON, metrics, variables documentées, rollback et commande de déploiement. Créer, via Clever Tools/Terraform si les droits sont disponibles, l’application Docker et PostgreSQL managé sans mettre de secrets dans GitHub.
  • Kevin : confirme coût, organisation, région, DPA, moyen de paiement, domaine/DNS et le premier déploiement. Ces choix contractuels ne sont pas automatisables.
  • Hermes : après accord, déploie une version taggée, vérifie HTTPS, santé, login OIDC, backup/restauration documentée, logs, métriques et rollback. Une release suivante reste reproductible depuis CI.
  • Critère de sortie : un tag déploie un artefact connu, monitoring actif, restauration testée et rollback vers la version précédente documenté.

5 · Analytics et évolutions ultérieures

  • Hermes : maintenir Umami local isolé, puis préparer son déploiement HTTPS et le tracker Nuxt lorsque Kevin choisit son domaine/public ingress. Créer le site Umami, intégrer le tracker sans données personnelles et tester dashboard + événements.
  • Kevin : valide exposition publique, conservation des analytics, politique de confidentialité/consentement et accès dashboard.
  • Hors phase : migration Personal Hub, IA, invitations de proches, stockage de données et indexation longue durée des logs nécessitent chacun leur cadrage de domaine avant code.
